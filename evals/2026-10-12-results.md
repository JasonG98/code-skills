对象：本次改造后的四个技能，重点为 `vibe-to-arch`。旧版基准提交：`fdb79f7`。

## 方法与限制

使用当前 Codex 会话的独立子代理上下文，未指定另一模型；未记录精确模型构建号。无技能、旧技能、新技能分别运行一次相同的维护请求。另做六个边界请求的适用性走查，以及一个 Python 临时项目的实际执行。

这是小样本定性验证，不是多次采样基准、跨模型比较或 Claude Code 实测。边界走查让模型阅读了完整技能，因此不能当作“仅凭 description 自动触发成功”的证据。原始执行发生在临时目录，没有往源码库加入测试框架或运行产物。

## 相同维护请求的对照

输入见 [maintenance 场景](vibe-to-arch.md)：稳定 CSV 服务、私有 helper 改名导致大量测试失败、已有公开行为覆盖。

| 组别 | 实际观察 |
|---|---|
| 无技能 | 直接选择清理实现耦合测试；复用契约与税费测试；缺口先补再删 |
| 旧版 | 虽识别到测试耦合，仍要求五项毕业检查、阅读全部源文件、提炼 SPEC、用户确认后局部重建 |
| 新版 | 选择一个 helper 相关的测试切片；核查独有行为与有效顺序契约；复用测试，不预设改源码或生成新文档 |

旧版实际回复中的阻塞点是：“进入实施前，我会完成五项毕业检查”，并追问过去一年是否推翻过业务假设。新版则以核对相关契约和受影响测试为下一步。

这里的改进是移除了旧版造成的额外流程；无技能组已经给出合理方案，不能据此宣称新版普遍优于不使用技能。新版的保留价值在于稳定表达个人维护目标、边界和可重复验收方式。

## 边界走查

- 普通 README 错字、新建空 CLI：判断不需要架构技能。
- TypeScript 的 900 行模块，仅审计：不按行数拆分，不改文件，允许保持现状。
- 支付测试减半：保留或等效替代先授权、避免重复扣款的保护，拒绝以数字作为唯一删测依据。
- 明确重写存储模块：尊重重写范围，提出兼容、隔离验证和分别处理代码/数据回退，不切换生产。
- 有充分公共行为覆盖的 wrapper 简化：核查调用者后复用已有测试，不制造重复红灯。

这些是回复层面的观察；支付与数据迁移场景没有执行代码。

## 隔离项目实际执行

初始模块按 7.5% 计税并 HALF_UP 舍入，生成 CSV，负数抛出既定错误。六项初始测试全部通过。

执行代理只修改测试文件：删除两个内部调用 mock 测试，将负数错误检查迁到公开入口，保留已有契约，增加一项 CSV 转义及记录顺序的行为测试。最终五项测试通过。它保留了职责清楚的生产 helper，没有为了“精简”强行改生产代码或创建新抽象。

主代理检查了实际文件，并重新执行以下内存变体，每个变体运行同一套五项测试：

| 变体 | 实际结果 |
|---|---|
| 正常实现 | 5 项通过 |
| 两个私有函数重命名，并同步内部调用 | 5 项通过 |
| 税率改错 | 2 项失败 |
| 舍入方式改错 | 1 项失败 |
| 删除负数校验 | 1 项失败 |
| 改坏错误消息 | 1 项失败 |

变体没有写入生产文件。故障被检测说明这个小场景保留了有效保护，不等于覆盖所有 CSV 或金融边界，也不代表复杂项目的维护成本已有量化改善。
