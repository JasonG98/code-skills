# Converge to Core

目标：重构后的仓库只含核心功能、结构最简，并且核心算法没有被改坏。

这是一次允许破坏性的重构。数据格式、模型接口和参数命名、配置结构、目录结构都可以重新设计，不需要兼容旧数据、旧 checkpoint，也不要求历史实验可复现。必须保住的是核心算法的语义：它算什么、怎么算。

## 原则

- 核心由用户定义。你负责提供证据和建议，因为只有用户知道哪些算法语义必须保住。
- 从核心出发决定保留什么，不在核心依赖闭包里的东西默认不带进新结构。兼容不再是约束，所以不必逐项证明"这个没用"；风险转移到"保留集有没有收全"，由探索和冒烟测试来兜。
- 区分两类变化。格式、命名、结构上的变化可以随意改；语义上的变化不能悄悄改（见末尾"语义变化"一节）。
- 先有安全网再动代码，否则分不清重构和改坏。
- 目标是最简：不为重构引入新框架或多余的抽象层。
- git 就是归档。`pre-converge` tag 保存旧代码，被删的内容随时能从它找回，不需要 `legacy/` 目录。

## 流程

### 1. 对齐

先自己读 README、入口脚本和配置，能查到的不要问用户。然后与用户确认：核心实验和入口命令是什么；哪些算法语义必须保住；多卡、混合精度等路径是否还在范围内。

### 2. 安全网

不追求新旧结果逐位一致，只需要保证两件事：新管线能完整跑通；核心算法的语义没被改坏。

- **基线。** 工作区必须干净。打 `pre-converge` tag，在 `converge` 分支上工作。记下 Python 文件数和总行数，用于最后对比。
- **参考基线。** 在旧代码上用极小配置（小数据子集、几十个 step、固定种子）跑一次核心流程，存下 loss 曲线和最终指标。它不要求新代码逐位复现，只是粗粒度的参照：同样设定下，新管线的 loss 应该以相近的方式下降，指标在相近的量级。没有它，就发现不了"能跑但算错了"。容差由用户定。
- **冒烟测试。** 新结构上一条命令走通：数据 → 训练几步 → 评估 → 保存新 checkpoint → 用新代码加载 → 再评估一次。每一批重构之后都跑它，所以要快。
- **核心计算对照测试。** 重构会重写预处理、loss、指标这类纯计算。对其中语义关键的部分，用固定的随机输入，分别调用旧实现（从 `pre-converge` 取出）和新实现，比较输出。这样能直接定位语义偏差，不受随机数序列和结构调整的影响。只对确实被重写或迁移的关键计算做，不必全覆盖，验证完不必留在新仓库里。
- **运行环境。** 这些运行不能有外部副作用：关闭远程日志上传，输出写到临时目录，才能放心反复运行。

### 3. 只读探索，确定保留集

这一步不修改任何文件。产出 `CORE_MAP.md`：入口清单（训练、评估、推理脚本及其读取的配置）、配置到代码的映射、**保留集**（核心流程需要的全部代码及其依赖关系）、范围不明的内容。探索到足以确定保留集即可，不需要通读所有文件。

从入口出发，沿着 import 和配置映射追出依赖闭包。静态闭包常常不完整，因为实验代码大量使用动态分发：registry、装饰器注册、`getattr`、`importlib`、配置里的类名或 `_target_` 字符串。所以要做两件事：

- 对每一条配置到代码的映射，确认目标已经纳入保留集。
- 用 `coverage` 跑一遍核心流程做反向检查：被实际执行到、却不在静态闭包里的代码，说明有动态依赖漏掉了。

单卡覆盖不到的路径（多卡、混合精度、`torch.compile`）：在用户确认的范围内，就手动并入保留集；不在范围内，就按舍弃处理。

保留的文件里也有没用到的函数、分支和配置开关，用静态工具（例如 `vulture`）配合覆盖率找出来，直接删掉或重写，不需要逐项举证。

保留集之外的东西，舍弃的依据是"核心不需要它"，不需要花力气证明它"确实没用"。但如果某项看起来很重要、又不在保留集里，列入待确认交给用户，不要静默丢掉。

### 4. 分类并交用户审批

把每个文件、模块和重要的类归入下面四类之一：

| 类别 | 含义 | 处理 |
|---|---|---|
| 保留 | 核心流程需要（含工具和数据处理） | 带进新结构，按需重写 |
| 变体 | 备选模型、loss、数据集、训练脚本 | 由用户选定哪些存活，默认只留核心用到的那一个 |
| 舍弃 | 核心不需要（含一次性脚本、notebook、结果产物） | 不带进新结构 |
| 待确认 | 看起来重要但不在保留集，或证据不足 | 列给用户，默认舍弃 |

提交给用户审批的内容：保留集清单；变体的取舍建议（某个变体是否还有保留价值，只有用户知道）；新目录结构草案，保持小而扁平，围绕核心流程组织；预计的文件数和行数变化；待确认项。审批通过后才开始动手。

### 5. 重构

按主题分批，每一批之后跑冒烟测试，通过就提交，失败就回滚这一批。分批主要是为了出问题时容易定位。建议顺序（可按仓库情况调整）：

1. 一次性去掉舍弃类的内容，先让仓库缩到只剩保留集，并让冒烟测试跑通。
2. 在保留集内部精简：合并近似重复的实现；只剩一个取值的配置开关，内联；只有一个条目的 registry，直接引用；对每一层封装做删除测试：设想删掉它，复杂度是消失了（纯转发层，应该删），还是会在多个调用方重新出现（值得保留）。
3. 重新设计数据、模型接口和配置，按最简原则围绕核心流程组织。
4. 目录重组，用 `git mv` 保留历史。
5. 重写 README：一条命令训练，一条命令评估。脚本之间"先跑 A 再跑 B"之类的隐式约定在这里写成显式的入口。
6. 清理残留引用：搜索已删除的名字、配置 key 和文档链接。

涉及语义的改动单独成一批：先向用户说明，用对照测试确认，通过后再提交。

失败时回滚到最近一次通过的提交，再二分定位原因，不在失败的状态上继续叠改动。

`CONVERGE_LOG.md` 记录：保留集；整体舍弃的部分（按目录或模块分组，每组一句理由）；待确认项经用户确认后的处置；语义相关的改动及其对照测试结果。

## 哪些改动算语义变化

数据格式、参数命名、checkpoint key、配置 key、目录结构、随机数序列都可以随意变，结果不再逐位一致也没关系。要小心的是悄悄改变"算法算什么"的改动，这类改动即使冒烟测试全绿也可能发生：

- **数据预处理**：归一化、增强、tokenization、过滤、数据划分方式
- **loss**：各项权重、mask、reduction 方式、数值稳定性处理
- **评估协议**：指标定义、后处理、评估集合与划分
- **优化细节**：优化器参数、学习率调度、梯度裁剪、warmup、初始化
- **训练流程里的隐式约定**：某个阶段冻结了哪些参数、哪一步用 `no_grad`、EMA、混合精度下 cast 的位置
- **只在特定环境才执行的分支**：多卡、混合精度、`torch.compile`。单卡冒烟覆盖不到，在范围内的需要手动验证
- **import 副作用**：靠装饰器注册的类没有显式引用，删掉或搬动后只有运行到那个分支才会发现缺失

涉及以上任何一项：向用户说明，用对照测试确认，通过后再提交。

## 需要用户拍板的两个节点

第 1 步结束时（核心和必须保住的语义），以及第 4 步结束时（保留什么、舍弃什么、变体怎么取舍、新结构草案）。这两处是只有用户能做的决定，所以要等明确的确认。

确认之后，在 `converge` 分支上提交、运行冒烟测试和覆盖率都是安全的，不需要逐步征求同意，一路推进到完成。只在这几种情况停下来问：

- 需要用户决定的语义改动或待确认项
- 冒烟测试失败，二分后仍定位不到原因
- 下一步会改变核心算法的语义，而用户没有同意

## 完成标准

- 冒烟测试和核心计算对照测试全绿，并且在最终状态下重新跑过一遍
- 仓库里没有指向已删除内容的残留引用（import、配置 key、文档链接）
- 交付物齐全：重构后的代码、`CORE_MAP.md`、`CONVERGE_LOG.md`、前后对比（文件数、行数）、待确认清单、从 `pre-converge` tag 找回旧内容的方法
- 只看新的 README，能用一条命令训练、一条命令评估

如果用户希望在完成标准之外继续往下做（例如进一步合并相近模块），请他说明范围和停止条件。
