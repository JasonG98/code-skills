# 渐进迁移与重写判断

仅在模块边界需要改变、原型要继续演进或用户要求重写时读取。

## 先比较代价

局部修复适合问题集中、现有接口和业务逻辑可靠的情况。渐进替换适合旧边界反复阻碍变化，但仍须持续交付的系统。完整重写需要具体理由，例如核心技术约束无法满足需求，或可界定范围内的替换成本确实更低。

把现有代码当作行为证据和可复用资产。不能仅因它来自 vibe coding、缺少某种分层或文件较长就判定必须丢弃。用户明确要求重写时尊重范围，说明代价，保留已验证算法和有用测试。

## 建立足够的契约

从入口、调用方、真实使用样例、测试和现有记录提取输入输出、不变量、错误语义与兼容要求。区分有意行为、已知缺陷和仍不明确的行为；信息不足时只询问会改变方案的部分。

小模块可以在任务记录中写清。多团队接口、数据迁移或长期替换需要一份精简设计记录，复用项目已有位置；不要求同时新建 LEARNINGS、SPEC、ARCHITECTURE 和逐步审批文件。

## 按可交付切片迁移

选择一条端到端路径，列出旧入口、新实现、调用方切换、检查和回退方式。让业务路径尽早贯通，避免先构建大批尚无消费者的基础层。

每个切片要能独立验证。迁移确实需要的兼容适配器应标明消费者、移除条件和验证方式。无需对外兼容的内部转发层可以直接消除。

已有授权涵盖的可逆整理持续完成，不逐文件等待批准。公共 API 破坏性变更、不可逆数据迁移、对外发布等超出当前授权的动作，在具体方案可审查时确认。

## 数据与切换

涉及持久化数据时，检查 schema、历史数据、并发写入、幂等和回退限制。先在隔离数据或副本验证，再按已授权的发布流程切换。切流回旧代码不等于数据可回退；需要分别验证。

观察结果满足契约并且调用方已迁移后，移除可证实不再使用的旧实现、兼容层、配置、依赖和过期测试。外部消费者无法核实时，保留兼容并记录退出条件。

完成信号是目标变化已经变容易、关键行为可验证、旧路径有明确去向，而不是目录符合某张架构图。
