# 测试：保护行为，允许实现变化

在测试因内部调整大面积失败、套件难维护，或重构缺少保护时读取。

## 决定测什么

从失败风险选择最便宜而可信的验证层级：

| 风险 | 合适的保护 |
|---|---|
| 计算、解析、状态转换错误 | 直接调用真实逻辑的单元测试 |
| 数据库约束、序列化、适配器不匹配 | 针对实际边界的集成或契约测试 |
| 用户主流程无法贯通 | 少量代表性的端到端测试 |
| 纯重构，相关行为已有覆盖 | 复用现有测试，缺口才补特征测试 |
| 文档、格式、静态配置错误 | 链接、语法、构建或配置校验 |

一项测试应回答“哪种有价值的回归会被发现”。相同层级、相同行为的重复断言可以合并；不同层级保护不同故障时应保留。覆盖率用于找遗漏，不作为删测或继续添测的唯一依据。

## 整理已有测试

抽查实际失败的测试，识别它保护的是输出、状态变化、边界交互，还是私有函数名、内部调用顺序和对象构造方式。

- 复用已有契约测试。没有独立行为价值的重复测试可删除。
- 旧测试包含独有边界条件时，先把该条件迁移到合适的行为测试并确认通过，再移除旧断言。
- 若预期行为本身不明确，记录观察结果与风险，不把实现偶然行为自动确认为产品要求。
- 无法说明被删测试的保护由哪里接替时，保留它并报告不确定性。

测试数量下降只是可能的结果。真正的验收是：内部重命名或内联不会破坏无关测试，而真实的行为错误仍会被发现。

## 降低测试自身的复杂度

数据只需少量字段时直接构造；输入形状相同的案例用参数化；多处确实共享生命周期时再引入 fixture。fixture 保持依赖可见，避免为了几条测试创建 builder、测试基类或通用 DSL。

替身放在昂贵、不稳定或不可安全执行的边界，如网络、时钟和外部服务。关键数据库语义用真实数据库的隔离实例验证，不能仅靠 mock 证明。

普通内部协作优先执行真实代码。调用次数或顺序本身就是契约时仍可断言，例如扣款只发生一次、先授权后写入、失败后回滚；不因“少 mock”破坏这些保护。

## 验证删测没有失去保护

在变更说明中给出简短对应关系：旧保护 → 保留或替代的测试。先跑受影响测试，再按影响范围扩大。风险较高且替代保护有疑问时，用隔离环境中的定向故障注入或 mutation testing 检查它能否发现真实回归；恢复临时修改后再跑正常检查。不要求每次小重构建立 mutation 基础设施。

需求明确的新行为可先写失败测试再实现。已有特征测试应在重构前通过；它验证“行为不变”，不需要人为制造失败。一次性实验可用执行结果验证，高风险行为仍应有相称的保护。
