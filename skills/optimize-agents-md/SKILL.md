# 优化 AGENTS.md

AGENTS.md 每次会话都会进入 context，还会被不同的模型读到。目标不是把它变短，而是让 agent 在这个仓库里更自主、更可靠地把活做完。优化有两个方向：

- 去掉有害的：无用的指令占 context，互相矛盾的规则让 agent 犹豫，过度的约束让它变保守，过早停下来问、过度检查。
- 补上缺的：agent 自己无法得知的事实、什么算做完、哪些事可以直接做。

长度只是结果。优化后通常会变短，但缺关键信息时应该补，哪怕因此变长。

可以大胆动手：整体重写、重组结构，不必保留原文的措辞和顺序。改动靠 git 回退，不需要逐条向用户确认。

## 先看仓库

动手前先看 agent 能自己发现的东西：构建和依赖配置、linter 和 formatter 配置、CI、目录结构、README 和 docs、现有测试。"能不能自己发现"以仓库实际内容为准，不凭印象。同时核对 AGENTS.md 里提到的路径、命令、文档是否还存在，失效的就修正或删掉。

## 逐条判断

对每条指令问一句：删掉它，agent 会不会因此做错事，而且代价不小？

删除：

- 能从仓库读出来的内容：目录地图、技术栈、命令清单、代码风格。已有 linter、formatter 或 CI 强制的，必删。
- 模型本来就会做的事：先读代码再改、写计划、跑测试自检、写清楚的提交说明、总结改动。
- 每次编辑前必须通读若干文档或完整的 repo map。改一个 typo 不需要这些。
- 过细的步骤清单和流程。模型已经能处理模糊和细微差别，过细的指引现在反而会限制结果。
- 过期的、互相矛盾的、与 README 或 docs 重复的内容。
- 没有实际代价的"必须""禁止""绝不"。

改写：

- 强硬的"必须先问"，改成明确的边界。只对不可逆或代价高的动作保留确认，其余交给 agent 判断。以前为约束别的模型写下的限制，换成更强的模型后可能被过度解读，让它在你乐意它继续的地方停下来。
- "每次先读某文档"，改成带触发条件的指针。例如把"改动前先读 architecture.md、database.md、deployment.md"改成"架构边界看 architecture.md，改 schema 看 database.md，准备部署看 deployment.md"。
- 流程式指令，改成目标加约束：说清要什么结果、不能碰什么，怎么做留给 agent。

保留：

- agent 无法自己得知的事实：环境里的坑、隐含的约定、已被否决的方案及原因、非显然的架构约束。每条尽量带一句理由。
- 真正的红线：密钥和数据不入库、破坏性或不可逆的操作、发布和推送的授权、需要人来决定的事。
- 指向其他文档的指针，每条写明什么时候看。

补充：

- 仓库里能确认、但原文没写的非显然约定和环境坑，例如从 CI 配置、脚本注释、提交历史里看出来的。确认不了的不要编造，列进报告向用户提问。
- 完成标准。写明"做完"包括运行、检查结果、修复失败。除非确实需要人审，不要设"第一版完成后停下来等审查"。
- 对已知安全的工作流的明确许可，例如："本地测试使用一次性 fixtures，无法访问生产环境。直接运行，修复由本次改动引起的失败，并重跑受影响的测试，不必逐步确认。"
- 需要它继续探索时，说清探索什么、到哪里停。

## 目标结构

判断完每一条，再按下面的章节重新组织。标题可用中文或英文，跟随项目现有文档的语言。内容为空的章节不要建，某章节只有一两行时可以并入相邻章节。

必须：

- Product（项目）：一句话说明项目是什么、做给谁、跑在哪些平台，必要时加标识符、许可证这类身份信息。
- Boundaries（红线）：真正的硬约束，包括密钥和数据不入库、不可逆操作、提交推送发布的授权、必须由人决定的事。没有特别的红线时，也写明默认的授权规则。
- Conventions（约定）：必须保持的行为和不变量、非显然的约定、已被否决的方案及原因。这是 agent 最无法自己得知的部分，每条带一句理由。
- Done（完成标准）：怎样才算做完，哪些检查必须通过，对已知安全的工作流的许可，需要继续探索时探索什么、到哪里停。

可选，有内容才写：

- Structure（结构）：只写从目录里看不出来的模块职责、依赖方向和边界。
- Pitfalls（已知坑）：环境和平台差异、工具链版本要求、典型报错的真正原因。
- Docs（文档指针）：其他文档各自在什么情况下查阅。
- Glossary（术语）：项目自造、在代码里查不到含义的缩写和代号。
- Autonomy（自主范围）：哪些决定 agent 可以直接做，哪些情形要停下来问，提问时带什么信息。
- Workflow（协作约定）：提交信息格式、回复和注释的语言、文档同步规则，只写和默认做法不同的部分。

需要时可以补充其他章节，前提是里面写的是 agent 自己无法得知的内容。拿不准一条内容放哪里时，看它回答的是哪个问题：项目是什么，不能做什么，必须保持什么，怎样才算做完。

## 写法

- 用简短直接的陈述句，写事实和不变量，不写流程。
- 中英文之间不要生搬硬套地互译，术语和通用词保留原文，中英共存、适当夹杂更利于理解，已被硬翻译得难懂的地方要改回来。
- 一条只说一件事，同一件事不要在两处重复。
- 面向会读到它的所有模型写，不要针对某个模型的毛病打补丁。
- 内容多时，让 AGENTS.md 只做入口，细节放进 docs 并写明何时查阅。
- 不为了短而删掉有价值的信息，也不为了显得完整而保留噪音。一般几十行够用，超过一百行就逐条自问为什么需要。

## 边界

- 只改指令的写法，不改项目的实质约束，例如验收阈值、安全边界、授权要求。拿不准是不是红线的，保留并在报告里标出来。
- 如果仓库里还有 CLAUDE.md、嵌套的 AGENTS.md 等重复或指向它的文件，一并检查，避免两份指令漂移。

## 收尾

- 直接改写文件，除非用户要求，否则不提交。不是 git 仓库时，先留一份备份。
- 给用户一段简短报告：删了哪几类、各大约多少条；改写了什么；补了什么；保留了哪些红线；需要用户决定的事（最多三条）。不要逐条复述改动。
